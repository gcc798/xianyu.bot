# Go 代码可读性与可维护性规范

## 1. 适用范围

本规范是本仓库 Go 代码风格与开发质量要求的统一入口，适用于 AI 和开发人员新增、修改及评审的 Go 代码。

新增代码必须遵守本规范。修改历史代码时，应同步改善本次变更直接涉及的代码；除非影响正确性、安全性或本次需求，不得扩大到无关模块，也不得进行全仓格式化、重命名或注释补齐。

仓库根目录 `AGENTS.md` 中的工程边界、后端分层、API、安全、数据库、验证及交付规则仍然适用；发生冲突时，用户当前要求和更具体的 `AGENTS.md` 规则优先。

## 2. 核心原则

所有新增和修改的 Go 代码按以下优先级取舍：

1. 正确性：保证业务规则、数据一致性和边界条件正确。
2. 可读性：让熟悉 Go 的开发人员能够直接理解。
3. 简洁性：优先使用最直接、清晰的实现。
4. 可维护性：降低后续修改、测试和扩展成本。
5. 性能：在满足实际性能需求的前提下优化。

不得为缩短代码牺牲可读性，也不得为预留扩展引入尚无实际需求的抽象、设计模式或依赖。优先复用项目已有实现、Go 标准库和已引入的依赖。

## 3. 注释

### 3.1 类型和字段

- 新增业务结构体必须有中文注释，说明用途和职责。
- 导出类型的注释必须以类型名称开头，符合 GoDoc 约定。
- 结构体字段使用简短的中文尾行注释；涉及单位、范围、默认值、状态含义、缺失值或数据约束时，必须明确说明。
- 注释不得机械重复字段名，应补充真实业务含义。

### 3.2 函数和方法

- 导出的函数和方法必须有简短的简体中文 GoDoc，并以声明名称开头。
- 复杂函数无论是否导出，都必须在声明上方说明主要业务目的、关键约束和失败语义。
- 数据查询函数应说明关键筛选范围；聚合、转换函数应说明数据来源、完整性要求和缺失值处理规则。
- 简单非导出函数仅在业务含义、边界条件、副作用或设计原因无法从命名和代码直接看出时添加注释。
- 涉及数据库事务、外部调用、并发、重试或资源释放的函数，应说明关键行为和失败语义。
- 不得添加“获取用户”之类仅重复函数名称的注释。

### 3.3 常量

- 业务常量、状态常量和配置常量必须具有清晰语义。
- 数值涉及时间、容量、金额、功率或比率时，名称或注释必须明确单位。
- 导出常量必须遵守 GoDoc 约定。
- 不得在业务代码中使用缺少语义的魔法数字或字符串。

### 3.4 复杂流程

函数包含多个业务阶段，特别是事务、外部调用、并发控制、数据聚合或状态迁移组合时，必须按实际执行顺序添加中文阶段注释。读者应能通过职责注释和阶段注释理解主流程。

阶段注释应说明业务目的、原因和约束，不得逐行翻译代码。包含三个及以上业务阶段时，优先使用 `// 1：...`、`// 2：...` 的编号格式；同一函数内格式必须统一。简单线性函数不要添加步骤注释。

```go
// calculateSitePower 汇总站点全部有效功率测点；任一查询阶段失败时返回带操作语义的错误。
func (s *service) calculateSitePower(ctx context.Context, siteID int64) (float64, error) {
	// 1：获取参与聚合的设备，排除未启用和不支持的设备类型。
	devices, err := s.getSiteDevices(ctx, siteID)
	if err != nil {
		return 0, fmt.Errorf("查询站点设备: %w", err)
	}

	// 2：筛选有效功率测点，未配置测点的设备不参与汇总。
	points, err := s.getValidPowerPoints(ctx, devices)
	if err != nil {
		return 0, fmt.Errorf("查询功率测点: %w", err)
	}

	// 3：按统一单位计算有效测点总功率。
	return calculateTotalPower(points), nil
}
```

涉及事务和外部调用时，注释应突出调用边界与一致性原因：

```go
// confirmInvitation 向算法同步邀约，并仅在数据库快照未变化时提交确认状态。
func (s *service) confirmInvitation(ctx context.Context, invitationID int64) error {
	// 1：事务外读取发送快照并调用算法，避免外部请求长期占用数据库事务。
	snapshot, err := s.pushInvitationToAlgorithm(ctx, invitationID)
	if err != nil {
		return err
	}

	// 2：事务内锁定邀约并复核快照，阻止并发修改被旧结果覆盖。
	return s.commitInvitationConfirmation(ctx, snapshot)
}
```

### 3.5 注释质量

- 注释优先解释“为什么”，而不是机械描述“做了什么”。
- 修改逻辑后必须同步检查相关注释、Swagger 描述和示例。
- 不得保留错误、过时、无信息价值或与实现不一致的注释。

## 4. 命名与构造函数

- 遵守 Go 惯用的 CamelCase 和 mixedCaps，包名使用简短、清晰的小写单词。
- 使用明确的领域名称，避免无实际含义的 `manager`、`processor`、`runtime`、`platform`、`tmp`、`data1` 或 `process2`。
- `ID`、`URL`、`HTTP`、`API` 等通用缩写的大小写必须一致。
- 布尔值使用能表达判断含义的名称，如 `isEnabled`、`hasPermission`。
- 单位不能由上下文可靠推断时，应在名称中体现，如 `timeoutSeconds`、`powerKW`。
- 允许 `i`、`err`、`ctx`、`tx` 等 Go 惯用短名称，不得为延长名称而降低可读性。
- 构造函数命名为 `NewXxx`，并放在对应类型附近。

## 5. 函数与依赖设计

- 每个函数应具有清晰、集中的职责，优先使用提前返回降低嵌套层级。
- 独立业务校验、转换规则、可单独测试的算法，以及事务、外部调用和资源生命周期等语义边界，可以提取为辅助函数。
- 只有一两行且没有独立业务含义的逻辑，不得只为降低函数行数而拆分。
- 不设置机械的函数行数上限；函数过长时，应检查是否存在多个职责或可独立测试的语义边界。
- 直接依赖所需对象，不增加无业务价值的包装、接口、中间层、通用工作流、工厂或单实现接口。

## 6. 错误处理

- 不得无故忽略错误；确实可以忽略时，应通过上下文或注释说明原因。
- 需要识别错误类型时使用 `errors.Is` 或 `errors.As`，不得依赖错误文本匹配。
- 向上返回系统错误时，使用 `fmt.Errorf` 和 `%w` 补充有助于定位的操作语义。
- 必须区分参数错误、业务错误和系统错误，不得擅自改变现有公开错误语义。
- 同一错误不得在每层重复记录。错误、日志和响应中不得泄露密码、密钥、令牌等敏感信息。

## 7. 并发、事务与外部调用

- goroutine 必须有明确的启动、退出和取消机制，优先使用 `context.Context` 控制生命周期。
- 共享变量必须有明确同步方式；非显而易见的锁范围和顺序必须说明。
- channel 的发送、关闭和接收责任必须明确，不得存在明显的 goroutine 泄漏风险。
- 数据库事务应只包含必须原子提交的数据库操作；除非业务设计明确要求，不得在事务内执行外部 HTTP 调用。
- 不为使用并发而使用并发。

## 8. 仓库代码组织

- `api/` 处理 HTTP 输入输出，`service/` 处理业务，`model/` 定义数据，`api/router/` 注册路由。
- `service/` 平铺基础能力和闲鱼业务，不恢复 `system`、`xianyu` 子包。
- `agent/` 独立承载 Agent、MCP、Tool 和资源能力；`xianyu/` 只承载闲鱼协议、连接和 Agent Tool 适配。
- Service 不依赖 `gin.Context`，Agent 与 Service 不互相持有；Agent 通过 Tool 调用业务能力。
- 用户业务数据必须在 Service 校验 `owner_id`。
- 沿用现有目录、分层、命名和依赖注入方式，不得无故引入新架构层、设计模式、通用框架或第二套基础库。
- 稳定且重复出现的业务逻辑应合理复用；未出现实际复用的逻辑不得提前抽象。
- 不得修改与当前需求无关的代码，也不得擅自改变公开 API、数据结构、数据库语义和原有业务行为。

## 9. 测试

- 新增或修改的复杂业务规则必须有能够在逻辑回归时失败的测试。
- 缺陷修复必须优先补充能够复现缺陷的回归测试。
- 事务一致性、状态迁移、并发取消、幂等更新、协议转换和输入边界属于优先测试对象。
- 测试应关注可观察行为，不得为凑覆盖率而复制实现细节。
- 简单转发、自动生成代码和没有分支的显然逻辑不强制新增测试。
- 不得把模拟测试写成真实账号或真实交易验收。

## 10. 格式化与验证

所有 Go 代码必须使用 `gofmt`，且仅格式化本次变更的 Go 文件，不得造成无关文件变更。

完成修改后至少执行：

```bash
gofmt -w <本次修改的 Go 文件>
go test <受影响的包及必要的直接依赖包>
go vet <受影响的包>
git diff --check
```

优先执行业务目录中已明确的更具体验证命令。若全仓测试依赖本地配置或外部服务，应区分本次回归与环境问题，并如实报告未执行或失败的项目。

仓库未固定版本或 CI 未执行的工具，例如 `goimports`、`staticcheck` 和 `golangci-lint`，不得写成强制验收条件。

## 11. AI 工作流程

AI 修改 Go 代码时必须：

1. 完整阅读本规范，并阅读相关代码、调用方和适用业务文档。
2. 优先复用项目已有实现和代码风格。
3. 在最小必要范围内完成修改，不得夹带无关重构。
4. 检查注释、命名、错误语义、并发生命周期和资源释放是否与实现一致。
5. 为复杂逻辑和缺陷修复补充最小且有效的测试。
6. 执行适用的格式化、静态检查和测试，并如实报告结果。

## 12. 评审优先级

历史代码评审按以下顺序判断：

1. 正确性、业务约束和数据一致性。
2. 安全、并发、事务和资源释放。
3. 错误处理和外部协议边界。
4. 可测试性、可读性和可维护性。
5. 命名、注释和格式一致性。

缺少非关键注释通常不应与业务错误或数据风险同等阻塞。评审意见应指向具体代码和可观察影响，不得只复述规范原文。

## 13. 验收清单

每次完成 Go 代码修改后检查：

- 业务逻辑、边界条件和错误语义是否正确。
- 导出声明和结构体字段的中文注释是否完整、准确。
- 单位、范围、默认值、状态和缺失值是否明确。
- 复杂流程是否具有必要的阶段说明，函数职责是否集中。
- 是否存在深层嵌套、无意义抽象、重复逻辑或无关改动。
- 事务、并发、外部调用和资源生命周期是否清晰。
- 复杂逻辑和缺陷修复是否有有效的回归测试。
- 代码、注释、接口文档和测试是否保持一致。
- 适用的格式化、静态检查和测试是否已执行并如实报告。
