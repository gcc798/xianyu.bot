# Telegram 业务迁移计划

> 状态：迁移提案，尚未代表目标架构已经实现。本文中的现状依据当前代码；目标和步骤用于评审。

## 现状

- `telegram.bot` 使用 Telethon 维护 Telegram 连接、登录 Session、来源会话和消息访问。
- Python 同时承担来源扫描与缓存、成人内容筛选、智能选源、消息检索、候选文件筛选、资源任务队列、下载、上传和部分任务状态管理。
- “智能”模式会调用配置的模型，仅按来源名称和用户名对来源排序；模型不可用时退回本地元数据排序。排序后仍会遍历剩余来源，直到达到文件数量上限。它不对消息正文或文件内容做 AI 判断。
- “全部”检索所有符合条件的来源；“手动”仅检索用户选定的来源。
- Go 已维护 Telegram API ID/Hash 配置及 FloodWait 状态，并拥有统一资源目录、资源交付授权和 Agent 资源获取流程。
- Python 仍直接读写 Telegram 设置、来源、扫描、退群、资源任务、资源文件、资源来源和获取任务数据。Go 也会操作部分 `tel_resource_files` 数据，存在跨进程共享业务状态。
- Python 批量资源检索目前直接调用 AI 接口，并包含与 Go 资源交付流程并行的实现。

## 主要问题

- **业务规则分散**：选源、过滤、任务状态和资源登记分布在 Go 与 Python，规则容易出现差异。
- **状态归属不清**：Go 和 Python 对部分 Telegram 资源记录都有读写，难以确定谁负责事务、重试、删除和恢复。
- **Python 数据库耦合过深**：Telegram 执行器持有业务表访问能力，迁移或替换执行器时需要一起搬迁业务流程。
- **模型配置和调用重复**：资源智能检索在 Python 有一套 AI 配置和调用；目标应由 Go 统一模型配置、调用策略和失败回退。
- **任务恢复复杂**：队列、进度、取消和重启恢复由 Python 数据库状态驱动，而业务任务归属目标是 Go。
- **职责边界与部署描述不一致**：文件由 Python 下载、Go 登记，但旧任务/文件记录仍在 Python，实际所有权不够直观。

## 目标

- **Go 是 Telegram 资源业务的唯一所有者**：负责用户归属校验、来源目录、检索策略、AI 选源、候选、任务生命周期、合规规则、取消/重试、上传授权和资源登记。
- **Python 是 Telegram 协议执行器**：负责 Telegram 登录态、连接、会话/消息 API 操作、Telegram 文件下载，以及使用 Go 提供的短期预签名 URL 上传文件。
- **Agent/Eino 与采集业务分层**：Agent 负责自然语言交互和需要模型判断的任务；Go Service 负责确定性的业务步骤。智能选源可以调用 Go 配置的模型，但不要求整条采集链使用 Eino Graph。
- **数据库写入单一归属**：迁移完成后，除 Telegram 登录 Session 外，Python 不直接访问业务数据库。
- **用户可观察状态一致**：任务、文件、错误、取消和恢复状态以 Go 的持久化记录为准。

## 通信边界

| 调用方 → 接收方 | 通道 | 用途 |
| --- | --- | --- |
| Web → Go | REST API | 创建/查看/取消采集任务，管理来源，查询资源与任务状态 |
| Go Agent → 已配置 MCP Server | MCP | Agent 动态发现并调用外部资源能力 |
| Go 业务服务 → Python Telegram 执行器 | MCP | 调用 Telegram 会话、消息检索、消息读取和文件下载等协议能力 |
| Python → 对象存储 | HTTPS PUT | 使用 Go 为当前任务生成的短期预签名 URL 上传文件 |
| Python → Go | 不作为常规业务通道 | 仅在确有实时进度推送等需求时增加受限内部回调；不得继续由 Python创建或持有业务任务 |

MCP 在这里表示可发现、可调用的 Telegram 能力，不替代 Go 的前端 REST API，也不承载 Go 的业务数据库职责。文件传输使用 HTTP 预签名 URL 是数据传输，不意味着 Python拥有资源业务。

## Eino 使用范围

- 智能模式确实需要模型参与：Go 根据关键词和来源元数据请求模型排序；无可用模型时按明确的本地规则排序，并在任务结果中记录实际策略。
- 任务创建、权限校验、来源过滤、顺序执行、限额、状态更新、重试和登记使用普通 Go 业务代码。
- 只有当流程包含必须由模型决定的动态分支、规划或多轮工具协作时，才使用 Eino Agent/Graph 编排对应部分。不要仅为串接固定步骤而把整条任务包装成 Graph。
- Eino 不替代任务表、事务、幂等键、worker 恢复、取消和进度事件；这些仍由 Go 服务负责。

## 数据与表归属

| 当前数据 | 目标写入者 | 目标处理方式 |
| --- | --- | --- |
| `tel_settings.telegram_session` | Python（仅协议 Session） | 暂时保留 Session 读写；`account_name` 改为运行时信息或 Go 状态，不作为 Python 持久业务数据 |
| `tel_settings` 中 AI、成人模式等设置 | Go | 迁到 Go 的 AI/业务配置；Python 不再读取 |
| `tel_dialogs` | Go | 作为 Telegram 来源目录；Python 扫描后返回规范化会话元数据，由 Go 校验并保存 |
| `tel_scan_history`、`tel_leave_history` | Go | 迁入 Go 的扫描任务与操作审计能力；保留现有表或改名由 schema 评审决定 |
| `tel_resource_tasks` | Go | 资源采集任务的用户输入、选择来源、数量限制、状态和进度归 Go；评估扩展现有 Go 资源搜索/任务模型，必要字段不足时新增 Go 业务表，不盲目复用不同语义的表 |
| `tel_acquisition_tasks` | Go | 与候选资源获取任务合并到 Go 资源任务生命周期，保留幂等、阶段、进度和错误信息 |
| `tel_resource_files`、`tel_resource_sources` | Go | 作为迁移期文件执行记录读取；新流程由 Go 管理任务文件状态并最终写入 `xy_resources`、`xy_resource_sources`。确认用途后再决定保留为 Go-owned 运维记录或停止写入 |
| `s_telegram_api_configs` | Go | 保持现有 Go 归属；Python 经受限内部配置接口取用 API 配置并回报 FloodWait，不直连数据库 |
| `xy_resources`、`xy_resource_sources` | Go | 统一资源目录和来源追溯，继续由 Go 登记、授权和删除 |

旧表数据迁移前必须备份并核对 `owner_id`、资源对象键、来源引用和任务状态。历史数据不能默认开放给普通用户；不得在未验证映射与引用完整性前删除旧表或对象。

## 实施步骤

1. **冻结接口和状态模型**：定义 Go 侧采集任务、来源、候选、文件状态、错误码、幂等、取消和重试合同；定义 Python MCP 工具仅接受执行所需的 Telegram 引用及任务授权参数。
2. **补齐 Go 业务持久化**：由 Go 接管来源目录扫描结果、扫描/退群记录和批量采集任务。根据现有 `xy_resource_searches`、`xy_resource_candidates`、`xy_resource_tasks` 的真实语义决定复用或新增表；更新唯一初始化文件 `server/internal/infra/migrations/init.sql`，不让服务启动时自动建表。
3. **迁移智能选源**：将模型配置和 AI 调用放到 Go；实现来源元数据排序、模型排序、输入 ID 校验、无模型回退和实际策略记录。测试模型超时、无效 ID、空来源和本地回退。
4. **收窄 Python MCP 能力**：把 Telegram 会话列表/扫描、消息搜索/读取、指定消息下载等能力做成协议执行接口；移除其中的 AI 选源、成人策略、用户业务授权、任务创建和资源目录登记。MCP 输入不能成为绕过 Go 用户权限与合规校验的入口。
5. **接通文件交付**：Go 创建/更新任务并生成短期、限对象范围的预签名 URL；Python 下载到受控临时目录并 PUT 上传，返回大小、SHA-256、Telegram 消息引用和文件元数据；Go 验证对象后完成资源登记。失败、取消和临时文件清理需覆盖完整。
6. **迁移调用方**：资源任务页面和 Agent Tool 改为调用 Go 的统一任务 API/业务能力；Python 页面中仍需保留的 Telegram 登录、连接或基础运维页面不得继续操作迁出的资源业务表。
7. **切换数据库所有权**：先停止 Python 新增旧业务记录，再核对历史任务与资源映射；按备份、校验、迁移、只读观察的顺序处理历史数据。观察期结束并确认没有读者后，另行评审旧表清理，不与功能切换同批执行。
8. **移除旧路径并验收**：删除 Python 资源 AI 配置、业务 SQL、旧队列和 Go 对同一旧表的兼容读写；保留 Telegram Session 持久化。完成 Go/Python 自动化测试、前端构建和真实浏览器主流程检查。

## 验收标准

- Python 资源检索/下载流程不再连接或读写业务数据库；若保留 Session 存储，其访问范围仅为 Telegram 登录态。
- 同一个任务的创建、权限、来源、状态、进度、取消、错误、重试和资源登记均以 Go 为准。
- 智能模式能展示/记录实际采用 AI 排序还是本地回退；全部和手动模式不调用模型。
- Python 只能执行 Go 授权的来源与消息操作，不能自行扩大来源范围或改变用户归属。
- 文件经短期预签名 URL 上传；Go 校验大小和摘要后登记，失败不会留下错误的可用资源记录。
- 重启、重复提交、取消、限流、模型不可用、Telegram 不可达、上传失败及重复消息等场景有自动化测试覆盖。
- 旧表迁移和对象清理可审计、可恢复，不因切换导致用户资源或授权信息丢失。

## 范围外

- 不迁移或重写 Telegram 登录协议库；Telethon 仍可作为协议执行实现。
- 不将所有任务改造成通用工作流，也不建设工作流设计器。
- 不在本次功能切换中直接删除历史表、Session 或对象存储文件。
- 不把 Telegram API 凭据、Session 或预签名 URL 写入普通日志、Agent Prompt 或轨迹。
