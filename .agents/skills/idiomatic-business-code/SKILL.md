# Idiomatic Business Code（业务代码去模板化与适度设计）

## 目标与边界

编写像熟悉该项目的工程师维护的生产代码：业务清楚、结构简单、易改、易测、符合语言惯例。

- 正确性、明确需求、安全性、现有契约优先于代码简短。**不得以“避免过度设计”为理由删除必需的校验、授权、错误处理、事务、并发控制、观测或测试。**
- 不把此 Skill 理解为“永远不准接口 / 分层 / 抽象 / 防御性检查”。选择应基于当前可验证的需求，而非想象的扩展。
- 遵循用户明确要求和仓库现有约定；发现冲突时，说明取舍，勿擅自改动大范围代码。
- 修改现有项目时优先最小化差异；不要进行无关的统一格式调整和架构重写。

## 执行工作流（每次编码或审查都执行）

### A. 编码前：收集足够上下文

1. 定位本次真正要解决的业务动作、实体、输入、输出、失败路径和数据边界。
2. 阅读同模块的相邻代码、命名、包结构、依赖方向、错误处理与测试写法；能复用就复用。
3. 列出需要改动的最少文件；确认是否真的需要新增接口、层、公共工具或设计模式。
4. 若不确定需求，优先采取可逆的、最小的实现，并标出关键假设。不要凭空设计“未来可能支持”的业务。

### B. 编码时：先走最短可维护路径

- 优先沿用项目现有入口和依赖；先实现直观的业务流程，再抽取已经出现的重复。
- 仅在明确职责边界处拆分；避免把一条可读的业务路径切碎到多个文件、对象和跳转。
- 抽象需要能说清：当前解决了什么重复、复杂度、替换要求或边界问题，以及为什么直接实现不够。
- 对外输入、数据库、文件、网络、并发、插件进程等真实边界保留完整的错误处理和校验。

### C. 完成前：强制自审

检查本次新增及修改的代码，逐条回答：

1. 名称能否明确指向业务含义？是否存在含糊的 `item/items/data/result/runtime/manager/processor`？
2. 一个简单请求是否被无必要地拆成过多层？是否只是参数透传？
3. 是否新增没有真实消费者或仅单实现、无必要的接口？
4. 每个 nil / 空值 / 状态检查是否有真实的输入或状态来源？
5. 注释解释了“为什么/规则/约束”还是只复述代码？
6. 是否为了未来可能性创建通用框架、插件点、配置开关、设计模式？
7. 新文件是否具备稳定独立职责？是否可以并入现有模块提升可读性？
8. 是否保留了必要的权限、边界校验、超时、事务、幂等、并发安全与可观测性？
9. 是否改动了与任务无关的代码？
10. 已执行哪些格式化、静态检查、测试？不能执行时须说明，不得假称通过。

若发现违背规则，先修复再交付；不需要输出冗长的自检过程。

## 规则 1：领域命名优先，禁止空泛命名

### 原则

- 先命名业务对象和动作，再命名技术实现。结构体表明职责，函数体现动作，变量表明值的含义。
- 可疑词（非绝对禁词）：`item`, `items`, `data`, `info`, `result`, `runtime`, `context`, `manager`, `processor`, `handler`, `helper`, `util`, `common`, `base`, `generic`, `obj`, `temp`, `do`, `execute`, `process`。
- 遇到可疑词，问：“换个业务模块，这个名字是否仍然成立？”如果是，很可能过于通用，需检查是否能更具体。
- 不要机械重命名标准语言概念或已有清晰术语。`context.Context`、Go `runtime`、HTTP handler、数据库结果对象、局部循环变量等在准确时都允许。
- 避免语义重复：如 `plugin.PluginManager` 在语境允许时不如 `plugin.Registry`；但不得为消除重复破坏公开 API 兼容性。
- 缩写遵守项目惯例；Go 的常见缩写（ID、URL、HTTP、JSON）按现有风格处理。

### 反例与改进（根据实际业务调整，不要照搬）

| 避免 | 只有在实际职责匹配时才采用 |
|---|---|
| `RuntimeManager` | `PluginSupervisor`（负责插件进程生命周期） |
| `ItemProcessor` | `ShipmentAllocator`（负责装船分配） |
| `ProcessData` | `AggregateMinuteReadings`（分钟数据聚合） |
| `HandleItem` | `RestartPlugin`（重启指定插件） |
| `items []Item` | `orders []Order`、`plugins []PluginProcess` |
| `data map[string]any` | 有确定结构时使用具名领域结构体 |

局部极短作用域可使用 `i`, `v`, `ok`, `err` 等惯用名。禁止为了避免短名而制造冗长语法。

## 规则 2：反对过度封装与机械分层

- **按职责和真实边界分层，不按模板强制层数。** CRUD 不必自动生成 Controller → Service → Manager → Processor → Repository → DAO。
- 如果新增层只有“接收参数 → 原样转发 → 返回结果”，且不承担鉴权、校验、事务、领域规则、映射、缓存或外部依赖隔离等明确责任，优先删除此层。
- HTTP handler 可以负责请求绑定、基础校验、状态码与响应组装；业务规则复杂或被多个入口复用时再抽取服务；持久化操作可以直接放在符合现有项目惯例的存储边界。
- 不要为每个表生成一套重复的 CRUD 泛型架构；根据现有代码和业务复杂度确定。
- 不越过项目已确立的隔离边界（如规定 handler 不允许直接操作 DB，则应遵守）。
- 对每个新增层提出可检验的问题：“去掉这一层，会损失什么实际能力或使耦合、测试、事务边界明显变差？”没有充分理由就不新增。

## 规则 3：接口由真实需求驱动

- Go 中优先在**消费方**定义其真正需要的小接口，而非为每个 struct 创建 `XxxInterface` 或 `IXxx`。
- 单一实现不是禁止接口的充分条件：已有 mock / 测试替身、明确外部边界、依赖倒置要求或调用方确实只依赖小契约时，单实现接口合理。
- 如果只有一个实现，且没有可验证的解耦收益，直接依赖具体类型。
- 不仅仅为方便“将来替换数据库/消息队列”预设整套抽象；只有当前存在替换、隔离或测试需求才设计。
- 不为泛型、工厂、依赖注入容器而制造无价值接口。

反例：

```go
// 无意义的一对一配套接口
// type OrderServiceInterface interface { CreateOrder(context.Context, CreateOrderRequest) error }
// type OrderService struct { ... }
```

优先选择：具体 `OrderService`；只有调用方确有独立契约需求时才抽取接口。

## 规则 4：防御性编程以真实边界为准

- **必须校验**：HTTP/RPC 请求，配置和环境变量，文件/数据库/消息队列返回值，外部系统/插件上报，反序列化，权限与所有权，数组索引、数值溢出、并发共享状态，可能过期或缺失的资源。
- **保留**：为了避免 panic、数据丢失、越权、死锁、重复执行、污染状态所需的检查；以及静态类型无法保证的业务不变量检查。
- **谨慎移除**：由同一函数刚完成初始化、已在紧邻上游验证、并在当前控制流中能直接证明的不可能分支；但跨函数、跨 goroutine、跨 IO 边界不能凭感觉认定安全。
- 不编造“兼容性降级”吞掉真实错误；不随意忽略返回的 `error`。
- 对确有必要却不显然的校验，写注释说明失败来源和后果，而非套话。
- 不将可观测性、恢复机制、安全校验错误地当成“多余防御”。

## 规则 5：注释只解释有价值的信息

- 按项目语言要求写注释（若用户要求结构体、字段、函数中文注释全覆盖，应执行），但避免空洞描述。
- 优先解释：业务含义、特殊约束、边界情况、时间与单位、兼容原因、并发不变量、事务理由、协议语义、失败恢复。
- 不写“处理数据”“执行操作”“定义结构体”“返回结果”这种复述名称的注释。
- 复杂代码使用简洁的**段落注释**讲清时序和为什么；普通代码不按每行解释。
- 公开标识符注释遵守 GoDoc 等语言规范；需要全覆盖时写实质性说明，而不是为覆盖率制造套话。

反例：`// RestartPlugin 重启插件。`

改进：`// RestartPlugin 先停止指定插件进程，再按原启动配置拉起；重启失败时记录退出原因并保留故障状态。`

## 规则 6：拒绝投机式通用化

- 只支持需求已明确的实体、协议、数据流、配置与扩展点。
- 不把插件管理写成“任意资源调度框架”，不把订单处理改成“通用工作流引擎”，除非当前需求真的需要。
- 第一次出现的重复通常先保留可读实现；出现**稳定且实质相同**的多处重复后再评估抽取，不能按僵硬次数阈值决策。
- 避免 `map[string]any` 承载明确定义的业务模型；优先静态类型。
- 不默认创建 `BaseXxx`、`GenericXxx`、`AbstractXxx`、`CommonXxx`；如果必要，必须说明它解决的现有问题。

## 规则 7：文件和包按凝聚度组织

- 一个文件可以包含多个紧密关联的结构体和函数。文件不是“一个函数/一个类型”原则。
- 不因为函数只有几行就一定合并，也不因为类型是新的就一定分文件：看它能否作为独立职责长期演进。
- 避免只有几行转发逻辑、且没有独立语义的文件与包；相邻业务尽量让阅读路径连续。
- 文件名描述业务功能，不要泛称 `common.go`、`utils.go`、`base.go`，除非它们在该项目里有明确职责。
- 若拆分能隔离协议实现、平台差异、测试、不同构建条件、复杂度或清晰的领域边界，则拆分合理。
- 不为了减少文件数而形成过大的混杂文件。遵循现有包布局。

## 规则 8：设计模式必须有明确收益

- 默认选择普通函数、具体结构体、组合与清晰的控制流。
- 使用工厂：创建步骤或依赖组装确实复杂；不为 `return &T{}` 创建工厂。
- 使用策略：已经存在需要替换且确实有差异的行为；不为单分支预建多策略。
- 使用适配器：当前存在不同接口或外部协议需要转换；不为将来可能的供应商做空壳。
- 使用事件总线/插件机制：确有多方订阅、扩展或生命周期管理需求；不为一次函数调用引入事件系统。
- 使用设计模式时，能在一句话中解释具体收益；不能解释，就回到直接实现。

## 规则 9：Go 代码落地约束

- 使用 `gofmt`；尊重项目的 lint/test 配置和现有包命名。
- 错误采用明确上下文包装（如 `fmt.Errorf("create order: %w", err)`），避免同一错误多层重复堆叠无用文案。
- 使用 `context.Context` 表示请求取消、超时与调用上下文；不要混作装业务参数的万能袋。
- 并发仅在有真实吞吐、延迟或隔离需求时引入；goroutine 必须考虑取消、退出、错误传播和竞争。
- 数据库操作明确事务边界；不要为了少一层破坏一致性。
- 不滥用 `interface{}` / `any`、反射和不必要的泛型。
- 与 Gin / GORM 集成时，遵守仓库既有错误处理和事务约定，不套用通用框架模板。

## 规则 10：Vue / TypeScript 落地约束

- 变量和方法体现页面业务，如 `selectedOrders`、`submitCorrection`、`isSaving`，不要满屏 `items`、`handleData`、`useManager`。
- 组件按可复用的 UI 职责或清晰页面区块拆分，避免每个按钮、每三行模板都独立组件。
- composable 在确有跨组件复用、复杂状态协调或生命周期管理时提取；简单页面逻辑就地保留。
- 优先声明明确的 DTO / 领域类型；不要把 `any`、万能 JSON 与大型枚举当作逃避建模的捷径。
- 不破坏项目已有的 Vue3、TypeScript、Ant Design Vue 状态管理与组件组织惯例。

## 规则 11：任务范围与兼容

- 修 bug 只修相关根因和必要测试；不要借机重构整个模块。
- 公开 API、数据库 schema、消息协议、文件格式、前端事件契约的变更，须有明确需求或迁移方案。
- 现有错误处理、审计日志、运行日志、健康检查、恢复流程不能仅因看起来繁琐而删除。
- 如果需求明确要求某项看似“过度设计”的能力（比如可替换插件、强隔离、审计），必须实现，并合理组织代码。

## 最终交付格式

完成代码任务后，简要说明：

1. 实现了哪些业务行为、修改了哪些主要模块。
2. 如新增接口、层、设计模式或重要检查，用一句话说明其当前必要性；没有则无需专门提及。
3. 执行了哪些检查/测试以及结果；未执行的明确说明。
4. 存在的真实风险、假设或未完成项（如有）。

不要输出“已符合所有规范”之类无法验证的自我评价；以代码和检查结果为准。

## 失败条件（必须返工）

- 为普通 CRUD 自动制造多层无职责透传。
- 为每个 struct 例行添加一对一接口。
- 在缺乏证据时添加“以后通用”的框架、设计模式、配置开关。
- 代码命名不表达业务，且明显可用领域术语替代。
- 为凑注释覆盖率加入无信息量的模板注释。
- 为几行相关代码创建无独立职责的包装文件/包。
- 删除真实边界上的必要校验、错误处理、权限控制或并发保护。
- 无关重构超出任务范围，或声称运行了未运行的测试。
